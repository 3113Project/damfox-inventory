# TASK-0011 — Sincronizzazione Git sicura e automatica

## Titolo

Configurare una sincronizzazione automatica prudente tra il repository locale e GitHub.

## Epic

Development Infrastructure

## Priorità

Alta

## Stato

Planned

## Obiettivo

Aggiungere al progetto un meccanismo sicuro che:

- esegua automaticamente `git fetch` dal repository remoto;
- aggiorni il repository locale esclusivamente con fast-forward;
- aggiorni i file locali soltanto quando il working tree è completamente pulito;
- non esegua merge, rebase, reset o operazioni distruttive;
- lasci a Codex il push dei commit esclusivamente quando il task contiene `Push: YES`;
- produca log consultabili tramite systemd.

Il repository locale è:

`/srv/docker/damfox-inventory`

Il remote è:

`git@github.com:3113Project/damfox-inventory.git`

L'utente del servizio è:

`casa`

## Contesto

L'ambiente reale è:

- VS Code su PC Windows;
- connessione Remote SSH al server Ubuntu;
- Codex eseguito nell'estensione VS Code;
- repository locale sul server;
- GitHub come fonte di verità;
- remote Git configurato tramite SSH.

Il working tree può contenere modifiche backend in corso. L'automazione non deve mai nasconderle, sovrascriverle, aggiungerle allo staging o integrarle automaticamente.

## Operazioni ordinate

### STEP 1 — Verifica preliminare

Eseguire:

```bash
git status --short
git remote -v
git branch --show-current
git rev-parse --show-toplevel
```

Confermare:

- repository `/srv/docker/damfox-inventory`;
- branch `main`;
- remote SSH corretto;
- eventuali modifiche locali non correlate.

Le modifiche locali devono rimanere intatte.

### STEP 2 — Creare lo script versionato

Creare `scripts/git-safe-sync.sh` con Bash rigoroso:

```bash
#!/usr/bin/env bash
set -Eeuo pipefail
```

Lo script deve:

1. usare costanti esplicite per repository, branch e remote;
2. acquisire un lock non bloccante tramite `flock`, evitando esecuzioni concorrenti;
3. verificare che il percorso sia un repository Git;
4. eseguire sempre `git fetch --prune origin main`;
5. controllare modifiche tracciate, modifiche staged e file non tracciati;
6. se il working tree non è pulito:
   - non modificare i file locali;
   - non fare stash;
   - non fare commit;
   - non fare merge;
   - registrare che il fetch è riuscito ma il fast-forward è stato saltato;
   - terminare con codice 0;
7. se il working tree è pulito, confrontare:
   - `HEAD`;
   - `origin/main`;
   - merge-base;
8. se locale e remoto sono uguali, terminare senza modifiche;
9. se il locale è strettamente dietro al remoto, eseguire esclusivamente:

```bash
git merge --ff-only origin/main
```

10. se il locale è avanti al remoto, non eseguire push automatico: registrare lo stato e terminare con codice 0;
11. se le cronologie sono divergenti, non correggerle: registrare errore e terminare con codice diverso da zero;
12. non usare mai `git pull`, `git reset`, `git rebase`, `git checkout`, `git stash`, `git clean` o force push;
13. produrre messaggi chiari con timestamp;
14. non stampare chiavi, token o segreti.

Lo script deve supportare un'opzione `--dry-run` che esegua fetch e analisi, ma non il merge fast-forward.

### STEP 3 — Creare il servizio systemd

Creare `deploy/systemd/damfox-git-sync.service` come servizio `oneshot`.

Requisiti:

- `User=casa`
- `Group=casa`
- `WorkingDirectory=/srv/docker/damfox-inventory`
- esecuzione di `/usr/local/bin/damfox-git-safe-sync`
- dipendenza dalla rete disponibile;
- ambiente minimo e prevedibile;
- nessun riavvio automatico infinito;
- hardening compatibile con la lettura di `/home/casa/.ssh` e la scrittura nel repository.

Non applicare direttive di hardening che impediscano l'accesso alla chiave SSH o al repository.

### STEP 4 — Creare il timer systemd

Creare `deploy/systemd/damfox-git-sync.timer`.

Requisiti:

- prima esecuzione alcuni minuti dopo il boot;
- esecuzione ogni 5 minuti;
- `Persistent=true`;
- jitter moderato tramite `RandomizedDelaySec` per evitare esecuzioni rigidamente simultanee;
- target `timers.target`.

### STEP 5 — Creare la documentazione operativa

Creare `docs/01_Development/GIT_SYNC.md` con:

- scopo e limiti del sistema;
- distinzione tra `fetch` automatico e fast-forward condizionale;
- spiegazione che con working tree sporco il remoto viene aggiornato solo nei riferimenti `origin/*`, mentre i file locali non cambiano;
- spiegazione che Codex può leggere un task remoto non ancora applicato localmente con:

```bash
git fetch origin main
git show origin/main:docs/06_AI/TASKS/TASK-XXXX.md
```

- procedura di installazione;
- procedura di verifica;
- comandi per log e stato;
- procedura di disattivazione e rimozione;
- comportamento in caso di divergenza;
- divieto di push automatico generico e di hook `post-commit`;
- responsabilità del push secondo `GIT_WORKFLOW.md`.

### STEP 6 — Testare lo script in modalità dry-run

Rendere eseguibile lo script versionato e verificare:

```bash
bash -n scripts/git-safe-sync.sh
scripts/git-safe-sync.sh --dry-run
```

Il test deve preservare tutte le modifiche locali preesistenti.

### STEP 7 — Installazione

Se Codex può usare `sudo` senza richiesta interattiva:

1. installare lo script con proprietà root e modalità `0755`;
2. installare le unità systemd con modalità `0644`;
3. eseguire `systemctl daemon-reload`;
4. abilitare e avviare il timer;
5. avviare manualmente una volta il servizio;
6. verificare stato e log.

Se `sudo` richiede password o non è disponibile, non tentare workaround. Fermare la sola fase di installazione e riportare esattamente questi comandi al maintainer:

```bash
sudo install -o root -g root -m 0755 scripts/git-safe-sync.sh /usr/local/bin/damfox-git-safe-sync
sudo install -o root -g root -m 0644 deploy/systemd/damfox-git-sync.service /etc/systemd/system/damfox-git-sync.service
sudo install -o root -g root -m 0644 deploy/systemd/damfox-git-sync.timer /etc/systemd/system/damfox-git-sync.timer
sudo systemctl daemon-reload
sudo systemctl enable --now damfox-git-sync.timer
sudo systemctl start damfox-git-sync.service
systemctl status damfox-git-sync.timer --no-pager
systemctl status damfox-git-sync.service --no-pager
journalctl -u damfox-git-sync.service -n 50 --no-pager
```

La mancata disponibilità di sudo non impedisce la creazione, il test e il commit dei file versionati.

### STEP 9 — Git

Prima dello staging eseguire:

```bash
git status --short
```

Aggiungere esclusivamente i file autorizzati con percorsi espliciti.

Non aggiungere modifiche backend preesistenti.

Verificare:

```bash
git diff --cached --check
git diff --cached --stat
git diff --cached
```

Creare il commit:

```text
chore: add safe Git synchronization
```

Verificare:

```bash
git show --stat --oneline HEAD
```

Eseguire il push soltanto se il branch locale non è dietro `origin/main` e non esiste divergenza.

Se il branch locale è dietro perché questo task è stato creato direttamente su GitHub, non eseguire merge o pull mentre esistono modifiche locali. In tal caso:

- completare e committare i file autorizzati solo se Git consente un commit locale sicuro;
- non eseguire push;
- riportare che serve integrare la cronologia con intervento del maintainer;
- non usare force push.

## Cosa non fare

- Non modificare backend, database, Docker Compose o file applicativi.
- Non nascondere o cancellare modifiche locali.
- Non usare `git add .` o `git add -A`.
- Non installare hook che eseguano push automatici.
- Non memorizzare credenziali nel repository.
- Non usare `git pull` nello script.
- Non risolvere automaticamente divergenze.
- Non eseguire reset, rebase, stash, clean o force push.
- Non fare commit di file estranei.

## Condizioni di arresto

Fermarsi senza improvvisare se:

- il repository o il branch non coincidono con quelli previsti;
- il remote non usa SSH;
- servirebbe modificare o cancellare lavoro locale;
- lo script richiederebbe un merge non fast-forward;
- le cronologie sono divergenti;
- i test mostrano errori;
- l'installazione richiede credenziali non disponibili;
- il commit includerebbe file non autorizzati.

## Criteri di completamento

- Script versionato, leggibile e non distruttivo.
- Fetch automatico funzionante.
- Fast-forward esclusivamente con working tree pulito.
- Dry-run funzionante.
- Unit file systemd validi.
- Documentazione operativa completa.
- Nessuna modifica locale estranea inclusa.
- Stato dell'installazione chiaramente riportato.

## Knowledge

- GitHub resta la fonte di verità.
- Il repository attivo può contenere lavoro non committato.
- L'automazione deve privilegiare la conservazione del lavoro locale rispetto alla sincronizzazione immediata.
- Un `fetch` è sicuro anche con working tree sporco; l'aggiornamento dei file locali non lo è sempre.
- Il push resta un'operazione autorizzata dal singolo task, non un comportamento automatico generale.
- Quando il working tree è sporco, Codex può leggere file remoti tramite `git show origin/main:<percorso>` dopo il fetch.
